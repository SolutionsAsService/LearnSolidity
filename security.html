Security

Security: four ways to lose money

Each attack below was run against a real contract, then run again against the fixed version.

  1. Reentrancy: paying before bookkeeping
  2. Overflow is checked
  3. tx.origin is not the caller
  4. Loops that grow

01 Reentrancy: paying before bookkeeping

VulnerableBank sends ether before it sets the balance to zero. The attacker’s receive() runs during that send and calls withdraw() again, while its balance still reads 1 ETH.

Terms

reentrancy
Calling back into a contract while an earlier call to it is still running, before it has finished updating its records.
revert
A transaction that stops and undoes everything it did. The sender still pays for the gas used up to that point.

What it shows. One transaction re-entered 8 times. The bank went from 8 ETH to 0 ETH; the attacker contract ended holding 9 ETH, its own 1 ETH plus everyone else’s. Alice’s honest withdrawal then failed (“Transfer failed”). SafeBank zeroes the balance first (checks, effects, then interactions): the same attack reverted and it still holds 8 ETH. Older tutorials write the vulnerable version with balances[msg.sender] -= amount; under 0.8 that underflows on re-entry and reverts, which hides the bug instead of showing it.

02 Overflow is checked

A uint8 holds 0 to 255. Before 0.8, 255 + 1 silently became 0. Now it reverts, unless you ask for the old behaviour with unchecked.

What it shows. The checked addition reverted with Panic(0x11): arithmetic overflow or underflow. The unchecked one succeeded and the value wrapped from 255 to 0. Use unchecked only where you can prove the value cannot overflow.

03 tx.origin is not the caller

tx.origin is the account that signed the whole transaction; msg.sender is whoever called this function. A wallet that trusts tx.origin trusts every contract its owner touches.

Terms

tx.origin
The account that signed the whole transaction, however many contracts it passed through on the way.
msg.sender
The address that called this function directly: a person’s account or another contract.

What it shows. Alice called a fake “airdrop” contract, which called her wallet. The wallet saw tx.origin == Alice and paid: it holds 0 ETH. The fixed wallet checks msg.sender, which was the phishing contract, and refused (“Not owner”); it still holds 5 ETH.

04 Loops that grow

payout() loops over every member and writes to each one’s credit. Every join() makes the next payout more expensive, and a block has a gas limit: 30,000,000 here, as on Ethereum mainnet today, and a single transaction can use at most one block.

Terms

gas
The unit of work the network charges for. Every operation has a fixed gas cost; storing data is the expensive part.

What it shows. Every member here is a different account, as in real use. The payout cost 48,073 gas with 1 member and 1,550,537 for a repeat payout to 200: about 7,636 gas more for every member (measured between 50 and 200). A member’s first payout costs more, about 24,736, because their credit goes from zero to non-zero. At the repeat rate, a payout would pass the 30,000,000-gas block limit at roughly 3,926 members; from then on it could not run at all, and nobody would be credited again. Anyone can call join(), so anyone can push it there. The fix, PullPayout, counts payout rounds and lets each member claim their own share. Its payout cost 43,451 gas with 1 member and 26,351 with 200 (the first round writes a fresh slot); a claim cost 70,214 for member 1 and 53,114 for member 200. The size of the list no longer matters.

Every contract on this site was compiled with solc 0.8.28 and run in an in-memory EVM (EthereumJS, Cancun rules) when the site was built: 16 source files, 23 contracts, 494 transactions (96 listed on these pages; the rest are setup calls such as members joining, counted where they happen), 17 reverted on purpose. Run cd tools && npm ci && npm run build to reproduce every number. Nothing here is financial or security-audit advice.
